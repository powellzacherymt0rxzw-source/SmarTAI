## 1. 最终用户流程

顶部八步保持：

`新建任务 → 上传题目 → 审核题目 → 上传作答 → 校对作答 → 执行批改 → 复核批改 → 结果分析`

本轮把内部动作重新归位：

1. **上传作答**只负责作答文件、身份匹配方式、可选名单和“开始识别作答”。
2. 作答识别完成后进入**校对作答**矩阵和唯一连续详情页。
3. 校对完成后进入第 6 步的**批改设置**；上传作答页不再提前展示或保存批改模型与评分策略。
4. 教师点击“开启 SmarTAI 批改”后进入只读**批改任务摘要**。
5. 摘要明确显示 10 秒自动开始倒计时，并同时提供“返回修改批改设置”和“立即开始批改”。
6. 倒计时或立即开始都只调用既有幂等 `POST /tasks/:id/grade`；不会建立第二套启动接口。

这套顺序把“识别学生作答”和“怎样正式批改”拆成两个清晰决定，避免教师上传文件时被与当前动作无关的长配置打断。

## 2. 页面与交互实现

### 2.1 S01 上传作答

- canonical route：`/tasks/:id/submissions/upload`。
- 页面只保留 Figma 10 的单焦点层级：标题、八步流程、约 `900×230` 上传区、身份匹配区和单一 CTA。
- 未选择文件时 CTA 仍可点击，用行内错误和原生 `title` 明确提示；识别处理中则进入既有进度页。
- 没有可用模型时，后端返回稳定错误码；页面显示 BYOK 入口并携带精确 `returnTo` 返回当前任务。
- 删除旧的“文件 → 内嵌识别/批改设置”第二阶段和临时 `phase=settings` 状态；上传页不再复制 C01 表单。

### 2.2 S03 / S05 校对作答

- 总览 footer 的主动作固定为“进入批改设置”。
- 次动作在有异常时为“查看首个待处理学生”，没有异常时为“查看作答详情”。
- 唯一详情 URL 继续是 `/tasks/:id/students/:sid?question=:qid`；footer 次动作精简为“返回作答总览”，主动作“进入批改设置”。
- 题目搜索框与说明分成两个视觉层：搜索输入独占白底边框容器；其下方先显示筛选/中文输入说明，再由下一条独占行显示方向键说明，不在宽屏并排，也不塞进输入框容器。
- 学生搜索候选中，仍有身份或题目异常的学生使用浅橙底和“需处理”标记；正常学生不增加噪声状态。
- 异常题卡在题号旁提供明显的“确认已复核”。确认后以蓝色“已复核”替换橙/红问题状态；原始 flag 仍保留为审计事实。
- 修改作答正文或 flag 会自动把该格重新置为待复核，避免旧确认覆盖新内容。

### 2.3 C01 批改设置

- canonical route：`/tasks/:id/grading-setup`，归属顶部第 6“执行批改”。
- C01 继续只维护一份任务级无密钥配置：模型组合、补充资料、常用评分策略和折叠高级设置。
- 默认返回校对作答；保存成功进入 `/tasks/:id/grading/preflight`。
- 主动作改为“开启 SmarTAI 批改”，含义是保存配置并进入启动摘要，不是在当前表单内立即调用模型。

### 2.4 C02 批改任务摘要

- canonical route：`/tasks/:id/grading/preflight`。
- 页面只读展示题目/学生覆盖、标答/评分标准/测试样例准备度、专家组合、综合方式、评分策略和风险。
- 可启动时显示 10 秒倒计时、进度线和自动开始说明；“立即开始批改”取消等待并走同一启动函数。
- “返回修改批改设置”带安全 task-scoped return URL；外部 return URL 仍被拒绝。
- React 严格模式下使用单一触发 ref，计时器卸载时清理，确保自动启动最多提交一次。
- 已进入 grading 或后续状态时不再倒计时；页面仅作为历史配置快照或跳转到真实进度/复核阶段。

## 3. 后端合同调整

### 3.1 作答识别与批改设置解耦

`POST /tasks/{task_id}/submissions/parse` 不再要求任务已保存 `grading_setup`：

- 调用方明确传 `recognition_provider_id` 时，仍执行 owner、启用状态和可见性校验。
- 未显式传入时，选择当前用户的默认可用 provider。
- 不再从历史 `grading_setup.primary_provider_id` 暗中选择识别模型；教师替换作答文件时，旧批改设置不会改变识别决策。
- provider id 继续进入请求指纹和 job 快照，但不保存 API key。
- 无可用 provider 返回 `recognition_provider_not_enabled`，由前端提供 BYOK 恢复入口。

### 3.2 作答复核状态持久化

`StudentAnswerInfo` 新增：

```text
review_status: pending | confirmed
```

`PATCH /tasks/{task_id}/students/{student_id}/answers/{q_id}` 支持可选 `review_status`：

- 仅确认时不删除识别 flag；flag 继续说明最初为何需要关注。
- 修改 `content` 或 `flag` 且未同时明确确认时，服务端强制回到 `pending`。
- 缺失答案格仍只能为任务中真实存在的题目创建，继续使用 owner、工作流状态和 expected revision/CAS 门禁。
- 当前 TaskStore 仍为进程内存；迁移 PostgreSQL 时必须把该字段和上述重开规则一并迁移，不能退回浏览器本地状态。

## 4. Figma 与视觉约束

- 批改设置沿用 Figma 08/12 的单列密度与重要性分层；常用项外露，低频项折叠。
- 启动摘要沿用 Figma 12 的只读卡片几何；新增倒计时只使用主蓝色，不再引入新的卡片样式。
- 颜色只表达主动作、当前步骤、正常/已复核和需处理，不为普通说明增加装饰色。

## 7. S01 → S02 单击跳转纠正（2026-07-27）

- 用户在第 4 步点击“开始识别作答”后，只需这一次动作；后端返回 `started` 或 `already_running` 就直接进入 `/tasks/:id/submissions/progress`。
- 原问题不是缺少目标路由，而是 React Query 仍保留旧的 `problems_ready` 任务快照：S02 首次渲染会按旧状态退回上传页，稍后状态刷新后上传页才显示“查看识别进度”，造成伪二次确认。
- 修复在作答识别 mutation 成功回调中同步更新任务详情与任务状态两份缓存的 `status / parse_job_id`，随后再执行统一失效刷新。错误响应仍停留上传页展示原有恢复提示，`already_done` 仍直接进入校对作答，不用伪造进度。
- 隔离浏览器将后端任务详情与状态刷新故意延迟 800ms：单击“开始识别作答”后 URL 立即并持续为 `/tasks/T_QA_SUBMISSION/submissions/progress`，显示真实进度卡，页面内不再出现“查看识别进度”；控制台 `0 errors / 0 warnings`，未调用真实模型。

## 8. C01 视觉层级与资料选择收口（2026-07-27）

- 批改设置主卡宽度与任务流程正文统一，模型、补充资料、评分方式按一个由上到下的阅读顺序排列；不再混用多种底色和大小不一的内嵌卡。
- 模型区只显示真实可选模型；单模型状态是不可交互的文字徽标，不伪装成可点击下拉框。多模型时才显示真实综合方式选择。
- 补充资料区直接提供资料库搜索、逐项选择、本地上传、“同时加入课程资料库”和已选资料清单；空状态明确说明当前只使用题目、标答与评分标准。
- 首屏只外露严格度和是否允许部分分；评语语气、长度、语言、多采样、低置信阈值、修正建议和教师备注统一收入“高级设置”，折叠态以一行摘要说明当前值。
- 隔离 `T_grading_qa` fixture 验收第 6 步、模型状态、资料空态、严格度、部分分开关、高级设置摘要和主动作；页面无假控件，构建与类型检查通过，未保存配置或调用 provider。
