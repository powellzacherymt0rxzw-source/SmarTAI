## 1. 核心产品判断

当前前端最大问题不是不够好看，而是把太多概念同时摊开，导致教师不知道：

- 现在应该做什么。
- 下一步会发生什么。
- 哪些设置是必须的，哪些设置可以以后再调。
- 点了按钮是否已经生效。
- 后台是否正在处理。
- 当前任务卡在哪个阶段。
- 出错后怎么恢复。
- 识别结果、批改结果、分析导出之间的版本关系是什么。

后续设计必须从“教师能自然完成任务”出发，而不是从“把所有功能入口放上去”出发。

### 1.1 体验原则

- [ ] 一页一个主要任务。
- [ ] 任务工作流页面尽量单栏，自上向下推进。
- [ ] 不要左右分很多栏，不让用户一进入页面就信息过载。
- [ ] 不要卡片套卡片。
- [ ] 页面 section 可以自然分隔、折叠、列表化，但不要过度框住。
- [ ] 必须先让用户知道主线流程，再提供高级功能。
- [ ] 默认简单，高级设置折叠。
- [ ] 复杂概念可以通过简短说明、tooltip、inline help 帮助理解。
- [ ] 按钮文案本身要尽量清楚；tooltip 是辅助，不是用来弥补模糊按钮。
- [ ] 上传或启动后台任务后必须立即进入明确进度页。
- [ ] 进度页要显示当前阶段、子步骤、已完成数量、预计剩余时间、后台运行状态。
- [ ] 阶段完成后自动进入可校对/可查看的结果页，不要求用户手动刷新。
- [ ] 每个任务可以并行独立运行，不阻塞新建任务或查看其他任务。
- [ ] 历史页和任务总览要清楚显示每个任务进行到什么阶段。
- [ ] 重要错误不能让用户卡死在错误页，必须给出原因和恢复动作。

### 1.2 不是回到旧版

用户明确表示：不是完全回到旧版本设计，而是要设计出真正让人眼前一亮的好产品。

旧版值得参考的是：

- 上传 -> 识别 -> 确认 的直接感。
- 页面比较少干扰。
- 流程推动感强。
- 用户不需要一开始理解太多配置。

旧版不值得照搬的是：

- 原型工具感强。
- 页面美观度和精致度不足。
- 高级能力组织不成熟。
- 对多任务并行、知识库、复核、导出、版本管理的支持不够。

新版目标：

- 更像成熟教学产品。
- 更像教师长期使用的 AI 批改工作台。
- 既要简洁，又要聪明。
- 既要降低认知负担，又要把高级能力做得自然。

## 2. 总流程

后续推荐的主流程：

```text
新建任务
  -> 添加/识别题目
  -> 题目准备工作台
      校对题目
      配置评分标准
      配置标答
      配置编程题测试样例
      可手动填写 / 批量导入资料 / AI 补全缺失资料
  -> 批改配置确认
      专家组合
      资料范围
      评分策略
  -> 添加/识别学生作答
  -> 校对学生作答
  -> 批改前确认
  -> 批改进度
  -> 结果总览
  -> 学生/题目复核
  -> 教师确认复核完成
  -> 生成学情分析、导出报告、发布版标答
  -> 正式完成
```

### 2.1 为什么取消大而全的配置页

- 题目没有识别出来之前，教师很难准确设置逐题评分标准、标答、测试样例。
- 评分标准、标答、测试样例都应该绑定具体题号。
- 标答可能来自整本书答案、章节答案合集、讲义、截图或扫描件，需要 AI 提取。
- 编程题测试样例、测试脚本也要绑定到具体编程题。
- 因此这些内容放在题目识别后的题目准备阶段最自然。
- 正式批改前再汇总专家组合、资料范围、评分策略，避免用户一开始被配置项淹没。

### 2.2 题目准备阶段是否会重复

用户曾担心：

- 题目识别完后有一个题目页面。
- 之后 AI 补全评分标准/标答/测试样例后，好像又回到一个类似页面。
- 是否会让用户觉得重复。

最终方向：

- 不做两个重复页面。
- 始终回到同一个 **题目准备工作台**。
- 这个页面先显示总览表。
- 识别刚完成时，题干已填，评分标准/标答/测试样例可能为空。
- 手动填写、批量导入资料、AI 补全缺失资料完成后，仍回到同一个总览表。
- 区别只是每题资料配置状态从空白/缺失/低置信，变成已生成/已提取/待确认/已确认。
- 用户不会感觉跳到了重复页面，而是感觉同一个工作台逐步被填满。

## 3. 阶段门禁与状态

### 3.1 推荐状态机

```text
draft
  -> extracting_problems
  -> problems_ready
  -> grading_config
  -> parsing_submissions
  -> submissions_ready
  -> grading
  -> graded
  -> review_confirmed
  -> generating_analysis
  -> finalized
```

错误状态：

```text
任意关键后台阶段 -> error
```

但 `error` 不是死页，而是需要处理的状态，必须有恢复动作。

### 3.2 状态显示

| backend status | 中文显示 | English label | 用户含义 |
|---|---|---|---|
| `draft` | 草稿 | Draft | 任务已创建，尚未上传题目 |
| `extracting_problems` | 题目识别中 | Recognizing problems | 后台正在识别题目 |
| `problems_ready` | 题目已识别 | Problems recognized | 题目识别完成，等待进入题目准备 |
| `grading_config` | 批改配置 | Grading setup | 校对题目、补充资料配置、确认专家和资料范围 |
| `parsing_submissions` | 作答识别中 | Recognizing submissions | 后台正在识别学生作答 |
| `submissions_ready` | 作答已识别 | Submissions recognized | 作答已识别，等待开始批改 |
| `grading` | 批改中 | Grading | 后台正在批改 |
| `graded` | 批改完成，待复核 | Graded, pending review | AI 批改结果已生成，等待教师复核确认 |
| `review_confirmed` | 复核已确认 | Review confirmed | 教师确认最终结果，可以生成正式分析和导出 |
| `generating_analysis` | 分析与导出生成中 | Generating analysis and exports | 后台正在生成学情分析、导出报告、发布版标答 |
| `finalized` | 正式完成 | Finalized | 分析、导出和发布版标答已基于最终结果生成 |
| `error` | 需要处理 | Needs attention | 出现错误，但可恢复 |

### 3.3 最新显示规则

- [ ] 同一个位置不要同时显示中英文状态。
- [ ] 中文界面默认只显示中文，例如 `批改中`。
- [ ] 如果进入英文界面，显示 `Grading`。
- [ ] 双语状态表可以存在于开发文档和 i18n 映射中，不要在常规 UI 里堆叠显示。

### 3.4 未到阶段的页面

- [ ] 当前阶段之前的页面可以查看。
- [ ] 当前阶段之前的页面可以修改，但危险操作需要确认。
- [ ] 当前阶段之后的页面不可直接操作。
- [ ] 点击未到阶段时，页面提示当前任务还在什么阶段。
- [ ] 提供跳回当前阶段的按钮。
- [ ] 例如尚未识别学生作答时，结果页不可进入；提示“当前任务正在题目准备阶段，请先完成作答上传和批改”。

## 4. 任务总览

> 注意：旧设计稿中写作“任务驾驶舱”，后续前端实现改为“任务总览”。

### 4.1 页面目标

任务总览不是普通空白 Dashboard，而是教师进入系统后的工作台。

它应该回答：

- 最近有哪些批改任务。
- 每个任务进行到哪里。
- 哪些任务在后台运行。
- 哪些任务需要我处理。
- 哪些任务已经正式完成。
- 有没有待导出的报告。
- 有没有近期常见易错点可以查看。
- 能否快速新建任务。

### 4.2 主要内容

- [ ] 顶部显示清晰标题：任务总览。
- [ ] 主 CTA：新建批改任务。
- [ ] 任务列表显示：任务名、课程、当前阶段、进度、预计剩余时间、待处理数量、下一步动作。
- [ ] 任务状态不要过度彩色化；关键状态可以用少量颜色。
- [ ] 近期提醒可以包括：待复核、待导出、常见易错点、可复用资料组。
- [ ] 多任务并行状态要明显。
- [ ] 点击任务进入该任务当前阶段。

### 4.3 高光能力

- [ ] 近期任务智能推荐。
- [ ] 近期易错点自动汇总。
- [ ] 待复核任务置顶。
- [ ] 可继续任务置顶。
- [ ] 资料配置缺失任务提醒。
- [ ] 正式完成任务提供下载入口。

## 6. 新建任务

### 6.1 页面目标

新建任务只做最小必要设置，不要一开始塞满配置。

### 6.2 必填/主要项

- [ ] 任务名称。
- [ ] 课程或班级。
- [ ] 学科语言，默认 auto。
- [ ] 截止日期可选。
- [ ] 题目识别专家，可默认继承。
- [ ] 是否启用 OCR/识别增强，可默认关闭。
- [ ] 是否已有参考资料，可用轻量选项表达。

### 6.3 不应该一开始展示的内容

- [ ] 复杂评分策略。
- [ ] 多专家综合细节。
- [ ] 低置信阈值。
- [ ] 编程沙盒超时。
- [ ] 标答提取模式。
- [ ] 每题测试样例数量。

这些应放到题目准备或批改前确认阶段。

### 6.4 BYOK 门禁

- [ ] 如果没有 BYOK 或可用专家，关键按钮应该禁用。
- [ ] 按钮旁边或页面显著位置提示原因。
- [ ] 提供直接跳转 BYOK 配置页的按钮。
- [ ] 可以显示几秒后自动跳转。
- [ ] 不要让用户走到上传/批改半路才失败。

## 7. 添加/识别题目

### 7.1 添加题目文件

页面应保持上传优先：

- [ ] 大上传区域。
- [ ] 支持拖拽或点击上传。
- [ ] 支持 PDF、图片、DOCX、Markdown、TXT。
- [ ] 支持从知识库选择文件。
- [ ] 支持选择知识库分组。
- [ ] 支持选择全部课程资料库。
- [ ] 上传新文件时可选择是否加入知识库。
- [ ] 显示识别专家。
- [ ] 显示是否启用 OCR/识别增强。
- [ ] 主按钮：开始识别题目。

### 7.2 题目识别进度

上传后必须自动进入进度页。

进度页显示：

## 10. 评分标准、标答、测试样例

### 10.1 评分标准

评分标准可以：

- 教师手动填写。
- 从上传文件导入。
- 从知识库资料导入。
- 由 AI 生成。
- 由 AI 复核。

需要支持：

- [ ] 总体评分细则文字输入。
- [ ] 每题评分标准。
- [ ] 严格程度滑杆。
- [ ] 部分分开关。
- [ ] 批改注意事项自由文本。
- [ ] 评分标准 AI 生成后标记为待确认。

### 10.2 标答

标答一定最终要生成，但发布版标答应放在批改完成后，结合学生错误、AI 批改情况和更优解法针对性生成。

题目准备阶段的标答用于批改辅助和逐题核对，不等同于最终发布版标答。

### 10.3 标答导入模式

只保留两项：

1. **已按题整理**
   - 适合教师已经准备好本次作业逐题答案。
   - 例如 Q1/Q2/Q3 已分好段。
   - 或文件标题、题号与本任务题目基本对应。
   - 系统主要做题号匹配、格式整理和低置信提示。

2. **从原文提取**
   - 适合答案来源很长或不只包含本次作业。
   - 例如整本书课后答案、章节答案合集、讲义、截图或扫描件。
   - 系统需要先在原文中找到本次作业对应题目。
   - 再提取对应答案。
   - 需要标出原文片段和匹配置信度。

不使用第三项：

- 不设置“仅作为参考资料，不生成逐题标答”。
- 因为标答最终一定要生成。

### 10.4 编程题测试样例

需要支持：

- [ ] 是否有测试样例。
- [ ] 上传测试样例。
- [ ] 从知识库选择测试样例。
- [ ] AI 生成测试样例数量。
- [ ] 沙盒超时设置。
- [ ] 滑杆 + 输入框，兼顾不同使用习惯。
- [ ] 默认值清晰显示。
- [ ] 教师不满意时可展开编辑滑杆和输入框。
- [ ] AI 生成的测试样例在每个题目详情页可查看。
- [ ] 测试样例多时可以展开或跳转到单独页面。
- [ ] 可下载测试脚本代码。
- [ ] 编程题标答可是一份示例正确代码。

## 11. 批量导入资料与 AI 补全

### 11.1 批量导入资料

用于教师不想逐题填写的情况。

流程：

- [ ] 选择要导入什么：评分标准、标答、编程题测试样例。

- 将生成几道题的参考答案。
- 将生成几道编程题的示例正确代码。
- 将生成几道编程题的测试样例和测试脚本。

规则：

- [ ] 生成内容标记为 AI 生成，待确认。
- [ ] 不直接锁定为最终答案。
- [ ] 完成后回到题目准备工作台。
- [ ] 总览表状态更新。
- [ ] 教师可逐题确认或修改。

## 17. 结果总览

### 17.1 核心原则

`graded` 不等于正式完成。

批改完成后先进入：

```text
结果总览
  -> 学生/题目复核
  -> 教师确认复核完成
  -> 生成分析与导出
  -> 正式完成
```

这样可以避免教师尚未修正 AI 批改错误时，就消耗资源生成学情分析和导出。

### 17.2 结果页三层数据

1. **AI 原始批改结果**
   - 保留模型原始分数。
   - 保留模型原始评语。
   - 保留置信度。
   - 保留专家分歧。
   - 保留日志。
   - 用于追溯。

2. **教师复核后的最终结果**
   - 教师修改分数。
   - 教师修改评语。
   - 教师添加复核备注。
   - 形成 final result。
   - 是学情分析、导出报告、发布成绩、生成发布版标答的唯一数据源。

3. **正式分析与导出产物**
   - 学情分析。
   - 自然语言总结。
   - 导出报告。
   - 发布版标答。
   - 默认不在 `graded` 后立刻生成。
   - 等教师点击“确认复核完成”后生成。

### 17.3 结果总览内容

- [ ] 学生数。
- [ ] 题目数。
- [ ] 平均分。
- [ ] 低置信题次。
- [ ] 需复核题次。
- [ ] 当前数据版本。
- [ ] 分析状态。
- [ ] 学生 x 题目置信度热力图。
- [ ] 低置信复核队列。
- [ ] 专家分歧队列。
- [ ] 分数异常队列。
- [ ] 自然语言筛选。

### 17.4 自然语言筛选示例

- 错得最多的题。
- 低于 60 分学生。
- 证明题常见错误。
- 专家分歧大的题。
- 低置信但分数很高的题。
- 第 3 题需要复核的学生。
- 排序算法相关错误。

## 19. 学情分析、导出、正式完成

### 19.1 生成时机

用户提出“要不就等教师确认完再生成”，最终采用：

- 批改完成后不自动生成高成本分析/导出。
- 先显示低成本结果总览和复核入口。
- 教师复核并确认完成后，才生成学情分析、导出报告、发布版标答。

理由：

- 节省资源。
- 避免错误批改结果污染统计。
- 避免导出旧数据。
- 更符合教师真实工作流。

### 19.2 正式完成阶段

`finalized` 表示：

## 20. 可恢复错误

### 20.1 错误设计原则

错误要尽可能多信息反馈到前端，而不是直接出错页面卡住。

每个错误至少要告诉用户：

- 发生在哪个阶段。
- 是什么类型。
- 是否可恢复。
- 用户现在能做什么。
- 是否可以重试。
- 是否需要等待。
- 是否可以换专家/key。
- 是否可以重新上传。
- 是否建议新建任务避免覆盖。

### 20.2 后端错误字段建议

- `code`
- `phase`
- `recoverable`
- `retry_after_seconds`
- `user_action`
- `technical_detail`
- `job_id`
- `trace_id`

### 20.3 错误场景

BYOK 缺失：

- 禁用关键按钮。
- 显示原因。
- 显示前往 BYOK 配置。
- 可自动跳转。

API 超量：

- 显示等待时间。
- 提示稍后重试。
- 提供重试按钮。
- 提供切换专家/key 选项。

网络超时：

- 提供重试。
- 提供继续任务。
- 不要求从头新建。

解析失败：

- 显示受影响文件。
- 提供重新上传该文件。
- 提供新建任务避免覆盖。
- 显示技术细节折叠区。
